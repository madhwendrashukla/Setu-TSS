When an admin creates an event on the Events page (upcoming), they get a 'Pin to Homepage' toggle. When pinned, this exact event shows in homepage Section 2.
Rule
Only ONE event can be pinned at a time. Pinning a new event automatically un-pins the previous one (is_pinned set to false on the old record).
Field on events table

Implementation Note
On the backend, when PUT /api/admin/events/:id sets is_pinned = true, run an UPDATE query that first sets is_pinned = false for all other rows, then sets it true for this one. This guarantees only one pinned event exists at any time.

3.2 Pinning Logic
1
Admin creates or edits an event under the Upcoming tab in /admin/events.
2
A 'Pin to Homepage' toggle is available only for upcoming (is_past = false) events.
3
Admin turns the toggle ON for one event.
4
Backend runs: SET is_pinned = false for all events, then SET is_pinned = true for this event.
5
Homepage Section 2 fetches the event WHERE is_pinned = true and is_past = false, and renders it.
6
If no event is pinned, Section 2 either hides or shows a default 'no upcoming workshop' state — to be confirmed with design.

8. Update Flow — How Content Changes Reach the Website
Same flow applies to every section described above: Hero Slides, Events, Mentors, Gallery, Testimonials, Community Partners.
1
Admin logs into /admin (protected, JWT-based).
2
Admin opens the relevant section (e.g. Gallery) and adds/edits/deletes an item.
3
Frontend sends a request to the Express API (e.g. POST /api/admin/gallery).
4
If a file is involved (image), it is uploaded to AWS S3 first — compressed if large — and the resulting URL is saved to PostgreSQL via Prisma.
5
If it's a video, the YouTube/external URL is validated and saved directly — no S3 upload.
6
The public-facing page (e.g. homepage) calls the public API (e.g. GET /api/gallery) on next load and shows the updated content immediately — no redeploy needed.
